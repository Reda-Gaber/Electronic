# باك اند متجر عبدالنبي بي سي تيك

Node.js + Express + MySQL. الجزء المُنجز حاليًا: **قاعدة البيانات + تسجيل دخول الأدمن**.

## التشغيل محليًا

```bash
npm install
cp .env.example .env
# افتح .env وحط بيانات قاعدة البيانات بتاعتك (راجع database/README.md لو لسه معملتهاش)
npm run dev
```

السيرفر هيشتغل على `http://localhost:5000` (أو البورت اللي تحطه في `.env`).
جرّب `http://localhost:5000/api/health` في المتصفح — لو شفت `"السيرفر شغال 👍"` يبقى كل حاجة تمام.

## إيه اللي اتعمل في الجزء ده (Auth)

- **POST `/api/auth/login`** — تسجيل دخول بالإيميل والباسورد، بيرجع JWT token
- **GET `/api/auth/me`** — بيانات الأدمن الحالي (محمي — محتاج توكن)
- **PATCH `/api/auth/change-password`** — تغيير كلمة المرور (محمي)
- **حماية ضد محاولات التخمين:** 10 محاولات دخول كحد أقصى كل 15 دقيقة لكل IP
- **middleware `protect`** — جاهز يُستخدم على أي مسار جديد هيتضاف بعد كده
  (منتجات، طلبات...) عشان يضمن إن الأدمن بس اللي يقدر يوصله

## الجزء 3 — API التصنيفات والمنتجات

### عام (لواجهة المتجر — بدون حماية)
- **GET `/api/categories`** — كل التصنيفات + عدد المنتجات المنشورة في كل واحد (محسوب لحظيًا)
- **GET `/api/categories/:slug`** — تصنيف واحد
- **GET `/api/products`** — المنتجات المنشورة فقط، بيدعم query params:
  `category` (slug), `search`, `brands` (comma-separated), `minPrice`, `maxPrice`,
  `inStock=true`, `isNew=true`, `isFeatured=true`, `sort` (`newest`|`price-asc`|`price-desc`|`popular`), `limit`
- **GET `/api/products/:slug`** — منتج واحد بكل صوره ومواصفاته (404 لو مسودة أو مش موجود)

### محمي (لوحة تحكم الأدمن)
- **GET `/api/admin/products`** — كل المنتجات (بما فيها المسودات)، بيدعم `search` و `categoryId`
- **GET `/api/admin/products/:id`** — منتج واحد لأي حالة نشر (لصفحة التعديل)
- **POST / PUT / DELETE `/api/admin/products`** — إنشاء/تعديل/حذف منتج (بصوره ومواصفاته)
- **GET / POST / PUT / DELETE `/api/admin/categories`** — نفس الفكرة للتصنيفات
  (الحذف مرفوض لو التصنيف لسه فيه منتجات مرتبطة به)

كل استجابات المنتجات/التصنيفات مطابقة تمامًا لشكل `Product`/`Category` في
`client/src/types/index.ts` (نفس أسماء الحقول camelCase، والـ IDs بترجع كنصوص).

## الجزء 4 — API الطلبات (Checkout + تتبع الطلب)

### عام (Guest بالكامل — بدون أي تسجيل دخول)
- **POST `/api/orders`** — إنشاء طلب من السلة. الأسعار ورسوم الشحن بتتحسب
  من القاعدة نفسها وقت الطلب (مش من اللي بعته العميل)، عشان محدش يقدر يغيّر
  سعر منتج من الطلب. بيرجع الطلب كامل، شامل `id` عشوائي (UUID) يُستخدم في
  رابط صفحة تأكيد الطلب.
- **GET `/api/orders/confirmation/:publicId`** — لصفحة تأكيد الطلب مباشرة
  بعد الشراء (بدون حماية إضافية — نفس مستوى أمان الرابط العشوائي في الفرونت حاليًا)
- **GET `/api/orders/track?referenceNumber=...&phone=...`** — تتبع الطلب،
  لازم الرقم المرجعي ورقم الهاتف يتطابقوا مع بعض

### محمي (لوحة تحكم الأدمن)
- **GET `/api/admin/orders`** — كل الطلبات، بيدعم `status`, `search`
  (اسم/تليفون/رقم مرجعي), `dateFrom`, `dateTo`
- **GET `/api/admin/orders/:id`** — طلب واحد بالتفصيل
- **PUT `/api/admin/orders/:id`** — تحديث الحالة و/أو ملاحظات الأدمن الداخلية

**ملحوظة أمان مهمة:** الـ `id` اللي بيرجع في استجابة الطلب مش رقم القاعدة
الداخلي المتسلسل (1، 2، 3...) — ده UUID عشوائي منفصل (`public_id`) عشان محدش
يقدر يخمن أرقام طلبات عملاء تانيين بمجرد تغيير رقم في رابط صفحة التأكيد.

## الجزء 5 — API الإعدادات

### عام
- **GET `/api/settings`** — بيانات المتجر ومناطق الشحن (يستخدمها الفوتر
  وصفحة الـ Checkout لاختيار منطقة الشحن)

### محمي (لوحة تحكم الأدمن)
- **GET `/api/admin/settings`** — نفس البيانات (للعرض في صفحة الإعدادات)
- **PUT `/api/admin/settings`** — تحديث بيانات المتجر ومناطق الشحن مع بعض
  في طلب واحد. مناطق الشحن بتتحدّث كقائمة كاملة (مسح القديم وإضافة الجديد)
  عشان تدعم الإضافة/الحذف/التعديل في نفس الوقت من غير الحاجة لمقارنة كل
  منطقة لوحدها — بالظبط زي ما بيبعتها زرار "حفظ" في صفحة الإعدادات حاليًا.

## الجزء 6 — لوحة التحكم الرئيسية (Dashboard)

- **GET `/api/admin/dashboard`** — محمي. كل إحصائيات لوحة التحكم في استعلام
  واحد مجمّع بدل ما الفرونت يجيب كل الطلبات والمنتجات ويحسبهم بنفسه:
  - `totalOrders`, `pendingOrders`, `totalRevenue` (بدون الطلبات الملغاة)
  - `lowStockProducts` — منتجات متوفرة لكن 5 قطع أو أقل
  - `salesByDay` — إجمالي المبيعات لآخر 7 أيام (شامل كل الحالات، زي الرسم
    البياني الأصلي بالضبط) — التواريخ بترجع ISO خام، وتنسيق اسم اليوم بالعربي
    (مثلاً "الأحد") يفضل شغل الفرونت زي ما هو دلوقتي
  - `recentOrders` — آخر 6 طلبات، كل واحد فيهم معاه `shortCode` (مثال:
    `ORD-4`) محسوب من ترتيبه الزمني بين كل الطلبات، عشان الفرونت مش
    محتاج يجيب كل الطلبات بس عشان يحسب الكود ده زي ما كان بيعمل قبل كده

### تصحيح مهم من الجزء 4
لقيت وصلحت مشكلة: `GET/PUT /api/admin/orders/:id` كانوا بيدوّروا بالـ id
الداخلي المتسلسل، لكن `GET /api/admin/orders` (القائمة) كان بيرجّع فيها
الـ `public_id` (UUID) في حقل `id`. يعني لو الفرونت استخدم `order.id` من
القائمة عشان يفتح تفاصيل الطلب، كان هيفشل. دلوقتي التلاتة مسارات بيستخدموا
نفس القيمة (`public_id`) دايمًا — `order.id` بقى موحّد في كل مكان.

## الفرونت اتربط فعلاً

- `AdminLoginPage.tsx` بقى بيستدعي `/api/auth/login` فعليًا (مش شكل بس زي الأول)
- كل مسارات `/admin/*` بقت محمية بـ `ProtectedAdminRoute` — محدش يقدر يدخلها
  من غير تسجيل دخول صحيح (كان قبل كده مفتوح لأي حد)
- زر "تسجيل الخروج" شغال فعليًا في أعلى لوحة التحكم

**عشان الفرونت يقدر يتصل بالباك اند ده محليًا:** لازم يكون فيه ملف `.env` في
مجلد الفرونت فيه `VITE_API_URL=http://localhost:5000/api` (راجع `.env.example`
هناك).

**باج مهم اتصلح أثناء الاختبار:** عند إنشاء طلب (`POST /api/orders`)، الـ
`productId` بيوصل من الفرونت كـ string لكن الـ id في قاعدة البيانات رقم —
المقارنة المباشرة بينهم كانت بتفشل بصمت وتطلع خطأ 500. اتصلح بتوحيد النوعين
لـ string وقت المقارنة.
